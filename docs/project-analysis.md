# Аналіз проекту Smart Vineyard (Розумний Виноградник)

- Дата: 2026-06-18
- Версія коду: гілка `main`, `index.html` (~9 376 рядків, 684 КБ)
- Пов'язані документи: [AGENTS.md](../AGENTS.md), [ADR](adr/), [README.md](../README.md)

> Документ описує поточний стан, виявлені недоліки та пріоритезовані пропозиції з
> оптимізації. Архітектурні рішення зафіксовано окремо в [ADR](adr/) — цей файл не дублює їх,
> а оцінює якість реалізації та шляхи покращення.

## 1. Огляд проекту

Клієнтський SPA для точного виноградарства (умови Вінниччини). Уся логіка, UI та зберігання
працюють у браузері без бекенду. Ключові модулі: календар фаз, щоденник робіт, аналітика
САТ/GDD, калькулятори ризиків, бібліотека сортів (122), база препаратів (CRUD), розрахунковий
центр, AI-помічник на Gemini.

**Технічний профіль (за метриками коду):**

| Показник | Значення | Коментар |
|---|---|---|
| Розмір `index.html` | 684 КБ / 9 376 рядків | Монолітний файл |
| Дублікат `index_clean.html` | 652 КБ | Ручна синхронізація |
| Функцій | ~175 | Переважно в глобальній області |
| `getElementById` | 461 | Без кешування DOM-вузлів |

| `alt` / `aria-*` / `role` | 0 / 0 / 0 | Доступність відсутня |

## 2. Сильні сторони

- **Автономність і приватність** — повністю клієнтський застосунок, дані не залишають
  пристрій ([ADR 0002](adr/0002-localstorage-persistence.md)).
- **Нульова інфраструктура** — запуск без Node/Docker, тривіальний деплой статики.
- **Продумана доменна логіка** — коректні агрономічні моделі (САТ/СЕТ, правило «6-6-26»,
  оїдіум за вологістю), пресети, «reset to default» для базових препаратів.
- **Стійкість до зривів мережі** — кешування погоди в `localStorage`, офлайн-режим лайт-версії.
- **Документація для користувача** — детальний україномовний README.
- **Захисне читання сховища** — більшість `JSON.parse` обгорнуто в `try/catch`.

## 3. Виявлені недоліки

### 3.1. Архітектура та супровід коду
- **Монолітний файл 9 376 рядків** — складно орієнтуватися, рев'юити, мерджити; високий ризик
  конфліктів і регресій.
- **Дублювання `index.html` ↔ `index_clean.html`** ([ADR 0005](adr/0005-dual-entry-points.md)) —
  кожна зміна логіки потребує ручного дзеркалення; головне джерело розсинхрону.
- **Глобальна область імен** — ~175 функцій без модулів/неймспейсів; ризик колізій і
  непрозорі залежності.
- **Залишковий `gemini.md`** — описує невідповідну 3-шарову агентну архітектуру; вводить в
  оману (зафіксовано в [AGENTS.md](../AGENTS.md) як «ігнорувати»).

### 3.2. Продуктивність
- **Tailwind через CDN (JIT у браузері)** — не призначений для production: важчий рантайм, без
  очищення невикористаних класів ([ADR 0007](adr/0007-cdn-dependencies.md)).
- **Незакріплені версії CDN** (`chart.js`, `heic2any` без тега) — ризик ламких оновлень.
- **461 `getElementById` без кешування** — повторні пошуки у DOM у гарячих шляхах.
- **75 присвоєнь `innerHTML`** — повні перемальовування замість точкових оновлень; зайві reflow.
- **Один великий HTML** — увесь код парситься на старті, навіть для лайт-сценаріїв.

### 3.3. Безпека
- **Ключ Gemini у `localStorage` і в URL** ([ADR 0003](adr/0003-client-side-gemini-key.md)) —
  доступний будь-якому скрипту, потрапляє в історію/логи. Прийнятно лише для власного ключа
  користувача, але варто попереджати про ризик.
- **Відсутній CSP** (`Content-Security-Policy`) — за 75 `innerHTML` і вставки даних
  користувача/AI підвищений ризик XSS.
- **Вставка AI/користувацького тексту через `innerHTML`** без явної санітизації — потенційний
  вектор ін'єкції розмітки.

### 3.4. Якість коду та процеси розробки (DX)
- **0 автотестів** — агрономічні розрахунки (САТ, NPK, бакові суміші, ГК) критичні, але не
  покриті; регресії виявляються лише вручну.
- **Немає лінтера/форматера** — стиль і помилки не контролюються автоматично.
- **22 `console.log`** у production-коді.
- **Немає CI** — жодних автоматичних перевірок при пуші.

### 3.5. Доступність (a11y) та UX
- **Жодного `alt`, `aria-*`, `role`** — проблеми для скрінрідерів і клавіатурної навігації.
- **182 inline-`onclick`** — змішування поведінки з розміткою, ускладнює делегування подій і
  керування фокусом.

### 3.6. Розгортання
- **Дві платформи одночасно** (GitHub Pages + Vercel) без визначеної канонічної
  ([ADR 0006](adr/0006-static-deployment-topology.md)); README і `vercel.json` неузгоджені.
- **Службові артефакти `.superpowers/`** (теки brainstorm з `server.log`, `server.pid` тощо)
  закомічені в репозиторій і не внесені до `.gitignore` — варто додати їх до ігнорування й
  прибрати з історії (`.DS_Store` уже ігнорується).

## 5. Рекомендований план (поетапно)

**Етап 1 — Швидкі перемоги (низькі зусилля):**
O1 (пін версій), O2 (чистка логів/`gemini.md`), O4 (попередження про ключ), O11 (канон деплою).

**Етап 2 — Безпека та надійність даних:**
O3 (CSP + санітизація), O10 (експорт/імпорт JSON).

**Етап 3 — Якість і довіра до розрахунків:**
O5 (модуль розрахунків + тести), O12 (CI), O6 (доступність).

**Етап 4 — Продуктивність і архітектура (за зростання навантаження):**
O7 (Tailwind build), O8 (делегування подій), O9 (єдине джерело для двох версій — переглядає
[ADR 0001](adr/0001-single-file-vanilla-spa.md) та [ADR 0005](adr/0005-dual-entry-points.md)).

> Етапи 1–2 не порушують ключових ADR. Етап 4 (особливо O7/O9) частково переглядає рішення
> «без збірки» — перед впровадженням оновити відповідні ADR.
