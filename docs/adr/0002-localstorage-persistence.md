# LocalStorage як єдиний рівень зберігання даних

- Статус: Погоджено
- Дата: 2026-06-18
- Пов'язані ADR: [0001](0001-single-file-vanilla-spa.md), [0003](0003-client-side-gemini-key.md)

## Контекст
Застосунок працює повністю на стороні клієнта, без бекенду та бази даних. Користувачу
потрібно зберігати: чек-листи фаз, журнал робіт, базу препаратів (CRUD), кастомні сорти,
стан калькуляторів, історію САТ, координати, історію AI-діалогів та ключ Gemini. Дані
мають переживати перезавантаження сторінки й бути доступними офлайн без облікового запису.

## Рішення
Усі користувацькі дані зберігаються у `localStorage` браузера під простором імен
`viticulture-*` (плюс кілька історичних ключів: `weather-lat`, `satHistory`,
`phaseChecklists` тощо). Кожен модуль самостійно серіалізує свій стан у JSON під власним
ключем. Зовнішнє сховище (сервер, БД, хмарна синхронізація) не використовується.

## Альтернативи
- IndexedDB — відкинуто: складніший API, надлишковий для поточних обсягів даних.
- Серверна БД з акаунтами — відкинуто: суперечить принципу автономності та офлайн-роботи
  ([0001](0001-single-file-vanilla-spa.md)).

## Наслідки

### Переваги
- Повна конфіденційність і офлайн-доступність: дані не залишають пристрій.
- Простота: синхронна робота без мережевих залежностей.

### Недоліки / компроміси
- Дані прив'язані до браузера/пристрою; немає синхронізації між пристроями та резервного копіювання.
- Ліміт обсягу (~5–10 МБ) і ризик втрати при очищенні даних браузера.
- Немає міграцій схеми — зміни форматів ключів треба обробляти захисним кодом.

### Подальші дії
- Тримати ключі у просторі імен `viticulture-*` для нових фіч.
- Розглянути експорт/імпорт JSON як резервне копіювання та механізм перенесення між пристроями.
