# Делегування подій, винесення скриптів і жорсткий CSP

- Статус: Погоджено
- Дата: 2026-06-19
- Пов'язані ADR: [0001](0001-single-file-vanilla-spa.md), [0003](0003-client-side-gemini-key.md), [0007](0007-cdn-dependencies.md)

## Контекст
Початково вся логіка повної версії жила в інлайн-`<script>` всередині `index.html`, а взаємодія
— у ~184 inline-обробниках (`onclick`/`onchange`/`oninput`/`onsubmit`/`onkeydown`/`onkeyup`).
Через це CSP мусив містити `'unsafe-inline'` у `script-src`, що зводило нанівець захист від XSS:
будь-який впроваджений скрипт чи обробник виконувався б. Після переходу Tailwind на зібраний
CSS ([0007](0007-cdn-dependencies.md)) зник і `'unsafe-eval'`, тож лишалося прибрати inline.

## Рішення
Повністю усунуто inline-виконання JS у повній версії (`index.html`):
- **Делегування подій:** один диспетчер на рівні `document` (`initEventDelegation`) обробляє
  `click/change/input/submit/keydown/keyup`. Елементи позначаються `data-action="fn"`
  (+ `data-action-param`, `data-action-on`, або `data-*` для складних аргументів). Працює і для
  динамічно доданих елементів (через спливання). Складні обробники (multi-arg, `this`,
  `this.value`, `event`, складені вирази, присвоєння) обгорнуто в типобезпечні `dlg_*` функції,
  що читають аргументи з `data-*`/події.
- **Винесення скриптів:** обидва інлайн-`<script>` винесено у зовнішні файли `app.js` (уся
  логіка застосунку) та `sw-register.js` (реєстрація service worker). Завантажуються звичайними
  `<script src>` — без бандлера в рантаймі ([0001](0001-single-file-vanilla-spa.md)).
- **CSP:** `script-src 'self' https://cdn.jsdelivr.net` — **без `'unsafe-inline'` і без
  `'unsafe-eval'`**. `style-src` зберігає `'unsafe-inline'` (інлайн-стилі та `style=""` у шаблонах).
- **Сумісність id:** порівняння id у пошуках/фільтрах переведено на нестроге `==`/`!=`, бо
  `data-action-param` віддає id рядком, а частина id — числові (`Date.now()`).

Інваріанти закріплено тестами (`test/delegation.test.js`): 0 inline-обробників, 0 inline
`<script>`, CSP без unsafe-*, кожен `data-action` має функцію в `app.js`.

> Лайт-версія `index_clean.html` лишається на інлайн-скриптах і `'unsafe-inline'` (поза скоупом).

## Альтернативи
- CSP-хеші для інлайн-скриптів — відкинуто: крихко (будь-яка зміна ламає хеш) і не покриває
  inline-обробники.
- Залишити `'unsafe-inline'` — відкинуто: знецінює CSP.
- Бандлер/фреймворк — відкинуто: суперечить «без рантайм-збірки» ([0001](0001-single-file-vanilla-spa.md)).

## Наслідки

### Переваги
- Реальний захист від XSS: сторонній скрипт не виконається, навіть якщо проникне в DOM.
- Чистіша розмітка; делегування ефективніше для динамічних списків.
- `app.js` кешується окремо (PWA/браузер).

### Недоліки / компроміси
- Уся логіка тепер в `app.js` — великий файл; зміни розмітки й логіки у різних файлах.
- Нові інтерактивні елементи мусять використовувати `data-action`, а не `onclick`.
- Нові зовнішні джерела треба додавати в CSP вручну.
- Розбіжність із лайт-версією (досі інлайн) зросла.

### Подальші дії
- Нові обробники — лише через `data-action` (+ `dlg_*` за потреби); жодних inline `on*=`.
- Нові зовнішні джерела — оновлювати CSP-мету.
- За потреби — застосувати ту саму міграцію до `index_clean.html`.
