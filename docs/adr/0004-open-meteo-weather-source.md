# Open-Meteo як джерело погодних даних і розрахунку САТ

- Статус: Погоджено
- Дата: 2026-06-18
- Пов'язані ADR: [0002](0002-localstorage-persistence.md)

## Контекст
Аналітика потребує погодних даних: поточних умов, прогнозу мінімальних температур
(приморозки), архіву середньодобових температур для накопичення Суми Активних Температур
(САТ) та Суми Ефективних Температур (СЕТ/GDD). Потрібне джерело без обов'язкового ключа,
з історичним архівом і безкоштовним доступом для клієнтського застосунку.

## Рішення
Використовується Open-Meteo: `api.open-meteo.com/v1/forecast` (поточна погода, 14-денний
прогноз min-температур) та `archive-api.open-meteo.com/v1/archive` (середньодобові
температури за сезон). Запити йдуть напряму з браузера за геокоординатами користувача
(`weather-lat`/`weather-lon`). Відповіді кешуються у `localStorage`
(`viticulture-weather-current-cache`, `forecastDailyTemps`) з відмітками часу синхронізації.
САТ рахується як сума `(T_середня − 10°C)` за дні з `T_середня > 10°C`.

## Альтернативи
- OpenWeatherMap / інші платні API з обов'язковим ключем — відкинуто: вимагають реєстрації
  ключа й ускладнюють безсерверну роздачу.
- Ручне введення температур — лишено як резервний/калібрувальний режим, але не основний.

## Наслідки

### Переваги
- Безкоштовний доступ без ключа; наявний історичний архів для зворотного розрахунку САТ.
- Кешування зменшує кількість запитів і дає базову офлайн-стійкість.

### Недоліки / компроміси
- Залежність від доступності та стабільності схеми Open-Meteo API.
- Точність прив'язана до координат сітки моделі, а не до конкретної ділянки.

### Подальші дії
- Зберігати параметри запитів (`temperature_2m_mean`, `past_days`, `timezone=auto`)
  узгодженими між модулями прогнозу й архіву.
- За зміни контракту API оновити парсинг і кеш-ключі.
